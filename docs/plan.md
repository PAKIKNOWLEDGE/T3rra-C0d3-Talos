# Talos 实施计划与后续路线

本页是实施方案与未来规划的唯一正本，来自主人确认的浏览器单会话闭环计划及补充落盘要求。当前执行位置、环境核验结果、授权边界和验收结论只见 [status](status.md)；协作规则见 [workflow](workflow.md)，源码与实测依据见 [adapter](adapters/minimax-code.md)，视觉正本见 [design](design.md)。

第一部分是已确认的实施方案，按轮交付；第二部分是后续规划入口，不能直接当作开工清单。本文中的工程、接口和产品地址均为待实现约定，不表示已经存在或可运行。实际命令只在实现后写入 [README](../README.md)。

## 一、浏览器单会话闭环

### 1. 目标与范围

沿用已验收范本，完成真实对话、流式输出、工具详情、审批、取消，以及**运行中刷新页面后继续观察同一回合**。每轮交付后等待主人验收；只有收到“推进”才进入下一轮。失败先修本轮，不一次执行全部轮次。

- 主人负责更新 CLI 来对齐本地 MiniMax 源码；执行者先复核 Node、CLI 路径、版本及能力，不自行升级全局软件。相同版本号不自动证明安装产物与源码完全相同，仍需握手与探针验证。
- 沿用现有账号、模型和数据目录；测试 cwd 单独建立且可丢弃，测试会话会保存在现有引擎数据目录。不复制凭据，不自动改写权限规则。
- 原 `demo/` 保持原样，产品在独立目录实现。保留空间关系、字体、动效和 reduced-motion，不因接引擎重新设计。
- 本阶段不包含 Tauri、安装包、多会话并行、队列/steering、文件树、搜索、独立 diff 编辑器、终端面板、图片或发布。工具详情仍可安全展示引擎实际返回的文本。
- 不自动提交、推送，不修改 Rhodes 或其他外部参考仓库。引擎 fork 是相邻的自有仓库，只有当前轮明确授权时才修改；Talos 与引擎始终通过 ACP 对接，不用子模块或内部导入。

### 2. 工程与边界

采用 npm、TypeScript strict、Vite、原生 DOM、Vitest；不引入组件库重新设计。依赖使用精确版本并生成锁文件，ACP SDK 固定 `1.3.0`，使用稳定入口，不使用实验性 ACP v2。锁文件纳入项目交付，Git 提交仍遵从主人授权。

按应用核心、MiniMax 适配器、派生视图、UI、宿主 I/O、启动组合层分工。单向事实流为：

`引擎 → 适配事件 → 合并事实 → 派生视图 → UI`

TypeScript 应用核心是唯一业务状态源，本阶段由 Node 应用服务承载。UI 仅发送动作、读取视图，不直接调用 ACP；宿主模块只负责子进程、stdio、退出观察和有限清理，不复制业务状态机。核心不得依赖浏览器 DOM 或 Node 进程 API；系统能力通过接口注入，为未来 Tauri 迁移保留边界，不预先建第二套宿主。

一个服务持有一个引擎进程、一个 ACP 连接和一个当前会话。新建会话仅在当前回合结束后允许。工作区由启动参数 `--cwd` 指定并验证为现存绝对目录；首版不提供目录选择按钮，界面准确显示目录。

Windows 启动优先解析 npm 安装包 CLI 入口，以明确 Node 可执行路径和参数数组运行，避免 PowerShell 管道改写 stdio。无法解析时给可见错误，不猜路径、不拼接任意 shell 字符串。stdout 交给 SDK 协议处理，stderr 单独收集；只清理自己创建的进程。

### 3. 契约与状态约束

实现前按 [adapter](adapters/minimax-code.md) 核对源码证据、实际请求形状和缺失字段，再建立内部契约，不从 demo 推导引擎能力。

- 应用动作包括连接、创建、发送、取消、回复审批、恢复当前会话和重新连接引擎；每个动作有稳定 `operationId`。
- pending 保存请求方法、目标 sessionId 和进程代次；load 成功不依赖响应再次返回 sessionId。恢复使用原始 cwd 和历史加载，不拿应用目录替代会话目录。
- 引擎事件携带进程代次、sessionId，以及实际存在的 messageId/toolCallId。没有引擎 turnId 时使用明确标为本地的回合身份，不伪造上游身份。
- 连接、会话、回合、审批状态分开保存；旧代次响应不得污染新状态。工具更新按 toolCallId 合并，缺失字段不清空已有值。
- 运行和待审批期间禁用再次发送，保留输入草稿。prompt 失败保留正文并提供恢复入口，不自动重发。
- 停止先显示“正在停止”，原 prompt 的权威结局才决定中止或完成。取消等待超时只表示“尚未确认”，提供诊断与显式重连入口。
- 审批卡动态显示引擎实际提供的选项及 optionId，支持简单问卷通过同一通道出现。重复回复、过期回复和取消后的点击不能再次提交。
- 审批文案不能承诺“仅本次操作”；批准、拒绝和全局规则的作用域以证据为准。拒绝后再批准的验收使用不同新会话。
- 首版只声明已实现的客户端能力；不声明文件读写、终端、表单 elicitation、计划展示和终端认证，不启用 MiniMax 扩展通知。未知反向请求返回明确协议错误并显示诊断，不静默等待。
- 模型、权限和模式首版展示引擎报告的当前值，不实现配置编辑或登录界面。usage、工具位置等缺失就标明未报告，不从样张补值。

### 4. 刷新、恢复与服务

Node 服务持续持有 ACP 连接；浏览器断开不关闭引擎。浏览器通过同源 WebSocket 接收带 `serviceEpoch`、`revision` 的完整派生视图快照；流式快照最多每 50ms 合并推送一次，审批和终态立即推送。

重连先取得最新快照，再订阅后续版本；不从浏览器重发 initialize、prompt 或审批响应。运行中的文本、工具、待审批请求均从服务现状恢复。同 operationId 的动作在服务存活期间只执行一次。第二个页面可以观察，已有控制页面在线时禁止第二页提交动作。

服务或引擎真正重启与浏览器刷新分开处理：仅将当前 sessionId、cwd 等恢复定位信息持久化到忽略目录；重新 initialize 后加载历史。中断回合结局未知就保留未知，不承诺跨进程不断流，不自动补发 prompt。

服务仅监听 `127.0.0.1`，验证 Host/Origin；不开放任意 shell 执行或任意文件读取接口。开发服务由主人在外部终端启动，前端 HMR 不重启应用核心或引擎。产品默认端口为 `5193`，保留 demo 的 `5192`；端口占用直接报错。启动命令和实际访问地址在工程建立后写 README。

> **此处可能需要 Astra 把关**：第 3 轮涉及唯一状态源、请求身份、控制页面归属，第 5 轮涉及快照衔接、重复动作及进程重启。以上方向已经确定，局部实现无需重复问主人；若准备更换状态归属、改变恢复承诺、加入缓存截断或丢弃身份记录，先按 workflow 完成针对性的设计复核，不得以简化为由删掉刷新或去重验收。

### 5. 分轮实施与停止点

| 轮次 | 实施内容 | 验收终点 |
| --- | --- | --- |
| 1：环境、证据与握手 | 补齐源码证据；建立最小 TS 工程、可重跑探针；核对 Node、CLI 路径与版本；执行 initialize，记录协商能力和 stderr 分离结果 | 可重复获得真实握手；环境不支持、版本不符时准确停止。不创建会话、不调用模型 |
| 2：真实单会话探针 | 独立 cwd 中创建会话、文本 prompt、流式收集、取消、新进程 load 后继续；工具与审批探针 | 脱敏 trace 分别证明正常结局、取消结局、历史恢复、审批效果。未触发审批不能标通过 |
| 3：应用核心与本地服务 | 从探针抽取适配器；实现请求关联、事实合并、动作去重、错误恢复、派生视图；建立宿主生命周期和 WebSocket 接口 | 集成测试证明观察者断开不停止引擎、重复动作不重复执行、旧代次不能污染新状态 |
| 4：沿范本接入界面 | 接入新建、输入、流式回复、停止、工具详情、审批、事件视图、概况收放和错误恢复 | 主人能在原构图内完成真实对话与工具操作；所有可见控件有动作或明确静态原因 |
| 5：刷新、历史恢复与收口 | 运行中刷新、待审批刷新、页面断连、服务重启后的当前会话恢复；补齐失败路径与文档 | 刷新后同一回合继续且无重复；服务重启后历史单份、cwd 正确、可继续输入；未知结局可见 |

第 1 轮只有最小握手工程；Vite/UI/WebSocket 等按所属轮次引入，不提前堆出空壳。每轮均按 workflow 做适用检查、交付具体动作、等待主人验收并更新 status。

### 6. 界面接入

- 左栏仅显示 Talos 当前会话，不自动加载用户全部既有会话。
- 保留主阅读面、工单摘要与详情浮窗、黄色主操作及 reduced-motion。流式更新仅更新受影响节点，不整页重绘、抢焦点或强制滚到底。
- 文本首版安全地按纯文本及换行显示，不执行模型输出中的 HTML。
- 右栏 usage 有实际数值才显示；计划标明“暂未接入”，文件区域使用“工具涉及路径”，不冒充改动清单。
- 演示状态按钮从产品移除；模型和模式改为当前值说明，不保留假按钮。原 demo 不动。
- 建立待建的 `app/ui-manifest.json`，静态和动态元素均登记 `wired` 或 `static: 原因`。

### 7. 检查与验收场景

逐步建立真实的总闸，覆盖类型、单测、控件清单、模块边界、构建及现有两项 Python 检查。未实现的闸登记缺项，不造空成功脚本。命令只在 README 维护；禁止无头浏览器、Playwright/Puppeteer，jsdom 仅用于未来 `test/` 下的 DOM 结构断言。

重点测试：

- stdio：UTF-8 跨块、LF/CRLF、尾帧、stderr 隔离、异常退出。
- 会话：load 响应无 sessionId、历史顺序、加载失败解锁、cwd 不匹配。
- 合并：工具部分更新、重复快照、连续相同文本片段不能被错误去重。
- 竞态：双击发送、审批重复点击、迟到响应、取消与正常完成同时到达。
- 恢复：浏览器断线时模型继续输出或提出审批，重连后恢复同一事实。
- 故障：缺少 CLI、登录失败、未知反向请求、引擎退出、新旧进程代次隔离。
- 清理：正常退出只清理应用拥有的进程，不按进程名杀用户服务。

使用 SDK 假引擎和 Node WebSocket 客户端做确定性测试，只证明产品处理逻辑；真实 MiniMax 探针单独报告。探针保存在仓库内，原始 trace 默认忽略，仅保留经过审查、来自合成输入的脱敏证据。不把用户账号、环境变量值或私人会话写入日志和证据。

每轮交付须给实际启动命令、前置条件、URL/文件和 3–5 个顺序动作及预期，独立列机读结果。最终至少覆盖：

1. 发送“只回复 `talos-ok`，不要调用工具” → 真实回复，完成后可继续输入。
2. 请求较长回复，在输出中刷新 → 同一回合继续，指令和回复不重复；随后停止并核对真实结局。
3. 触发源码与探针确认的审批场景，在审批中刷新 → 请求仍可处理；拒绝后核对无目标文件。
4. 新建测试会话执行批准场景 → 选择实际提供的非永久选项，核对文件内容；卡片消失不算写入成功。
5. 空闲时重启服务、恢复当前会话 → 历史单份、目录正确、可以继续输入。

若现有权限规则导致审批不出现，记录实际行为并停止该项验收；不得擅自改变用户规则或以模拟审批替代。机读通过不升级为人工验收。

## 二、浏览器闭环之后的规划入口

以下是方向、依赖和验收目标，不是已完成设计，也没有自动实施授权。只有当前阶段完成验收、主人选定下一目标并授权推进后，才为所选阶段补齐决策完整的小轮计划。不得因这里出现一个功能就提前建接口、引入依赖或扩张当前闭环。

### A. Tauri 2 宿主方案与最小桌面窗口

前置：浏览器五轮完成验收，核心与系统 I/O 边界已验证；保留浏览器开发入口。

> **此处可能需要 Astra 把关**：浏览器版的业务核心运行在 Node 服务中，不能把“套 Tauri”理解为直接打包开发服务器。桌面实施前必须确定核心放置位置、Node 服务是否成为受控 sidecar、Rust/IPC/transport 的职责，以及服务与窗口的生命周期。不得临时换成 Electron，也不得在 Rust 中复制第二套业务状态机。

需先产出并在本节补齐：选定的核心承载方案及依据、开发与桌面入口的差异、IPC 命令/事件边界、运行时依赖和数据落点、窗口关闭/重载/崩溃的含义。未经这一步，不默认用户机器装有 Node，也不默认安装包会捆绑 Node 或 MiniMax。

建议小轮：先做复用产品资产的本地窗口与 I/O 往返，再接入单会话真实引擎，最后验证重载和退出。窗口出现不等于引擎已接通；本阶段不承诺可分发安装包。

验收需覆盖同一范本的桌面显示、真实文本流、审批、取消、引擎缺失的恢复提示，并增加 Cargo fmt/check/clippy、宿主测试和生产资产检查。

### B. Windows 工作区与进程生命周期

前置：桌面核心承载与进程所有权方案已确定；可拆成独立验收轮，不与窗口、打包一口气完成。

> **此处可能需要 Astra 把关**：Windows 进程树、stdin 存活、退出回收、重启代次和原生目录选择会改变 I/O 边界。先明确谁创建、谁持有、谁关闭，不能用“窗口正常”或“spawn 成功”代替双向通信和退出验证。

规划内容：原生目录选择确定后自动导入、取消不改路径、失败/超时恢复；中文和空格路径；应用目录与项目 cwd 分离；缺引擎/版本不兼容时的诊断；仅清理自有子进程及其明确归属的后代。先定目录切换时对当前运行和历史身份的处理，再接 UI。

验收包括选目录的确定/取消/失败、实际项目读写、重启后的原 cwd、关闭/重载/异常退出和用户自启 mcode 不被误杀。杀进程不能冒充取消得到权威结局。

### C. 会话与引擎能力扩展（按需求选择）

候选包括历史会话列表、跨 cwd 恢复、模型/模式/权限编辑、完整问卷与计划、usage 展示、多会话并行、队列/steering。它们不是一轮，也没有预定全做顺序；优先选主人提出的一个真实使用需求。

> **此处可能需要 Astra 把关**：跨会话竞态、队列/steering、权限作用域和配置 revision 会改变当前单前台模型。必须先重新取证，确定哪些字段是会话级、进程级或持久化全局级，再补契约、状态迁移和失败路径。不能从 TUI、demo 或 SDK 存在某方法推导 MiniMax 已支持。

每个扩展先给最小报文与脱敏探针、事实合并规则、旧记录缺字段处理、迟到事件隔离、UI 控件接线和验收步骤。会话 close、历史删除和实际数据销毁分开规划；不因有 close 就新增删除按钮。

验收重点是快速切换不串会话、配置不会被旧读回退、审批影响范围可见、继续会话 cwd 正确、失败能恢复。真实计划和 usage 替换缺失说明时仍须保持阅读区留白。

### D. 文件、diff、终端与辅助工作流（按需求选择）

候选包括文件树、真实改动视图、独立 diff、终端、搜索、导出和图片。先确定每项的数据来源及主人需求，再给独立小轮计划；不因 demo 有文件列表就实现完整文件管理器。

> **此处可能需要 Astra 把关**：文件写入、diff 应用、终端执行和图片输入引入新的系统能力与权限边界。必须先决定路径归属、工作区越界处理、写入冲突、取消和恢复，以及需要声明的客户端能力。图片还需当前引擎/模型证据；不能让 UI 先接受后静默丢弃。

只读的列表或展示可在证据明确后按普通小轮实现；可写和可执行功能先复核设计。diff 的预览不能等同于已落盘，工具 locations 不能等同于真实改动清单。终端需明确进程所有权和退出后状态；导出需明确内容及敏感信息边界。

### E. 安装包与发布准备

前置：桌面闭环与 Windows 生命周期通过，主人明确要求进入分发阶段。授权、资产、安装与升级均不因开发版可运行而算完成。

> **此处可能需要 Astra 把关**：安装包涉及核心运行时、引擎定位/分发、签名、更新机制及用户数据兼容。必须先定外置还是随包引擎、支持版本和架构、离线/缺依赖行为、升级失败恢复和卸载保留策略，不能由执行模型临时选择打包路线。

规划顺序：先检查字体、参考图和依赖许可，处理不可分发资产及公开文档链接；再做可复现生产构建和安装包；再验安装、启动、更新与卸载；最后才是主人授权的发布。自动更新是单独能力，除非主人明确要求，不默认为首个安装包附带。

验收须在符合目标前提的干净 Windows 环境检查：不依赖开发服务器、绝对本机路径或仓库 node_modules；引擎与账号前置清楚；安装/升级不会破坏历史数据；卸载不擅删账号和项目。debug exe 不能代替安装包验收。公开推送与发布沿用 status 中的授权边界。

## 三、规划防漂移与交接

实施前按 status 定位本轮，再读本文对应小节、相关证据和 workflow。本文有 Astra 提示的节点，复核机制见 [workflow](workflow.md)；这是风险位置提示，不代表任何模型已经审过，也不要求每次局部改动都切换模型。

已有明确方案内的修复、测试、接线可直接推进当前授权轮次。若证据推翻方案、验收无法满足或下一阶段仍有高影响决策，执行者整理具体冲突、可选方案及推荐项，留给主人安排 Astra 或指定的其他审阅者；不得擅自降低闸、删掉要求或把未来路线改成已授权实施。

复核结论更新本文的实现方案；源码事实更新 adapter；主人决定、验收和下一入口更新 status。保持一个计划正本，不另起“最终版”“新版”或不同模型各自的待办。

## 四、中立引擎 fork 路线与候选评估

本节记录已选定的两仓库路线，以及对 mcode fork、中立 custom provider、去 MiniMax 专属账号与产品品牌、Endfield 风格 TUI 的候选评估。依据为 [adapter 的 fork 取证](adapters/minimax-code.md#中立引擎-fork-评估取证2026-09-28)。路线已落地为两个相邻仓库，但代码中立化、TUI 改造和 GUI 修复仍按轮次授权，不因 fork 已存在就视为完成。

### 取舍与推荐

| 路线 | 能解决什么 | 主要维护成本 | 评估 |
| --- | --- | --- | --- |
| 只调整 Talos 品牌，使用上游已有 BYOK | 自有 UI、无需 MiniMax 登录的第三方模型 | 维护 ACP 适配和上游版本兼容；仍带上游专属功能/品牌 | 满足外壳和模型选择，不满足独立引擎发行目标 |
| 维护有限改动集的中立 fork | 自有 CLI/发行身份、默认 custom provider、独立数据、排除 MiniMax 托管服务，再沿主题接口美化 TUI | 持续审查账号、provider、构建/更新、协议和数据变化；执行回归 | 推荐用于长期独立产品，先做最小技术验证 |
| 大范围删除/改名并同时重写 TUI、运行时 | 可以全面定制 | 改动触及上游高频区域，每轮同步可能变成移植，需自担维护整个引擎 | 不建议作为起步；必须先缩小范围并单独论证 |

“去 MiniMax 鉴权”建议定义为：移除专属账号/订阅登录及默认服务依赖；模型使用用户明确配置的 provider 凭据。工具审批、沙箱、工作区权限和 provider 密钥保护仍保留。不能用删除门禁后继续调用原托管端点的方式实现中立化，也不承诺保留依赖厂商账号的全部云工具。

产品名与引擎来源分别处理：Talos 主阅读面使用自己的品牌；设置/诊断准确说明实际引擎和所选模型。替换产品 logo/文案并不需要删除 LICENSE、NOTICE、第三方归属；源码 MIT 也不意味着取得 Endfield 游戏素材、商标和字体的分发权。视觉延续本项目的原创工业风表达。

### 当前仓库地图与同步边界

当前采用两个并列仓库：

| 仓库 | 责任 | 边界 |
| --- | --- | --- |
| `C:\DEV\develop\T3rra-C0d3-Talos` | Talos GUI、产品文档、Endfield 族视觉与验收入口 | 只通过 ACP 使用引擎；不导入引擎内部模块，不持有引擎账号状态 |
| `C:\DEV\develop\minimax-code` | Talos 引擎 fork、CLI/TUI、provider、认证、会话与数据目录 | 遵守公开源码清单、许可证、第三方归属和同步规则；不把 GUI 代码复制进引擎 |

两仓库保留公开上游 Git 历史与提交基线；不使用 Git 子模块、不移动目录、不建立第三个仓库。Talos 通过稳定 ACP 和固定版本的引擎产物对接。CLI 名称、npm 包名、数据目录和更新源后续分别验证；当前 `.minimax` 账号与会话不做隐式迁移。首次切换失败可返回原版引擎，不能让同一数据目录在两个分支间反复升级。

将品牌/主题、provider/账号、云能力开关、发行/更新适配分为可复核的小提交；尽量保持未改模块的路径与标识符，避免全库字符串替换。最终发行不得保留可用的 MiniMax 专属登录入口或意外回退；分阶段禁用/隔离再裁剪，比未理清调用关系就删目录更易验证。

周期性同步的含义应为：选择公开上游的稳定提交或版本 → 在候选分支合入 → 审查冲突和新增网络/鉴权/数据迁移 → 跑回归 → 经审阅合入自己的分支。自动化可以提出同步 PR，不能无审查合入全部 PR。能减少差异的通用修复可考虑提交上游；发送 PR 或消息需另有相应授权。本次不创建定时任务或同步 PR。上游源码同步文档中面向其私有来源的流程不迁入本项目。

### 建议的最小验证轮与后续分轮

> **此处可能需要 Astra 把关**：这会增加一个长期维护的引擎产品。开始前须定清中立发行包含的能力、构建依赖、数据隔离、凭据存储、默认网络访问、上游同步闸及回滚方式。此节是源码支撑的可行性评估，不等于完整出口审计或 fork 已验收，也不自动批准删除安全与权限层。

1. **下一轮先验证独立引擎基础**：在新数据目录、没有 MiniMax 账号凭据的环境，使用真实 custom provider 完成 ACP 握手、文本、工具执行、取消和 load；复用上游 BYOK 测试但分别报告假 provider 与真实模型结果。默认模型缺失给明确配置入口，不能暗中回退托管模型。本轮已先落入默认关闭的 `TALOS_NEUTRAL_RUNTIME=1` 配置闸：它只阻止 managed/prod 自动种入或回填 MiniMax，不删除已有配置，也不等于真实中立发行完成。下一入口仍只做源码核对和最小可重跑探针，不直接删除鉴权代码。
2. **再形成中立发行**：先把 MiniMax、第三方预设和用户自建 provider 做成平级来源，取消按类型固定置顶和默认强绑定；再清理专属登录、品牌、更新渠道和云集成入口。审计 prompt 同步、模型目录、遥测和工具网络出口。构建中固定下载的 mcode-tools 要先确定可移除范围或替代，不承诺“本地源码独立构建”直至验证。无密钥本地 provider 是否纳入首版须明确。
3. **先交付 TUI**：对话流式终端；欢迎图使用 design 中的机械臂字符正本，名称为普通字号，不做大字字标。完整实现前先提供欢迎、对话/工具和审批三种画面范本；范本通过后沿既有主题和交互机制实现。布局、输入、滚动及中文宽度另轮验收；终端受字体、网格和颜色能力约束，不承诺复刻 Web 像素布局。
4. **再接回 GUI**：锁定引擎产物与 ACP 能力；补修状态页已记录的消息缺失和 UI 错漏，原浏览器验收要求继续有效。fork 本身不算修复前端消息问题。

配置入口的边界已经确定：最终产品在 TUI 中使用 `/provider`、`/provider add`、`/provider test` 和 `/provider list` 管理第三方 provider。Talos 浏览器的 `/provider-setup.html` 只是开发期真实接驳验收助手，不替代 TUI，也不作为最终产品能力承诺。TUI 范本验收时必须包含一次从 `/provider` 完成配置、测试、保存并切换默认模型的可见流程。

发行命令改名单独安排在 TUI 和 provider 流程稳定之后：先让 fork 提供 `talos` 入口并保留受控的 `mcode` 兼容别名，验证数据目录、ACP 启动、帮助文本、更新逻辑和脚本调用均已迁移；再决定是否移除 `mcode`。不在当前 provider 或 GUI 验收轮里做全库字符串替换。包名、数据目录、更新源、诊断中的引擎身份和许可证归属分别迁移，不能把命令改名当成品牌替换已完成。

最小验证应包括：断开厂商端点后指定模型仍可运行；文件工具真实落盘且审批可拒绝；取消与重启加载具有权威结果；原版数据和凭据未被读写；更新流程不会重新安装原版。网络测试需区分模型请求、用户选配 MCP/工具目标、默认厂商请求，不能以搜不到域名字符串替代运行证明。无法验证的云能力标为禁用或未提供，不伪装成功。

复杂 provider 兼容性、完整 TUI 重做和安装发布均不并入首轮。没有承诺几天完成；主题配色/文案成本较低，账号与默认路由剥离成本中等，彻底排除厂商服务/构建产物并长期跟随上游成本较高且持续发生。最小验证后才有依据估算后续工作量。
