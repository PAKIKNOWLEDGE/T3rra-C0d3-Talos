# 开发、验收与文档工作流

继承 Rhodes 持续奏效的协作节奏。本页定义做法，实施进度仅见 [status](status.md)。

## 0. 角色与交接

本项目采用主人显式指定的职责：`你是 Astra` 表示本轮架构设计或指定复核，`你是 Luna` 表示本轮日常开发全流程。这是成本分工，不是模型型号检测。按主人最近明确指定的角色工作，文件不能自行触发角色切换；主人最新指令优先于旧范围或分工。

默认由 Luna 在同一轮完成调查、局部计划、实现和自验，不把这些步骤拆成模型交接。交接卡是同一张任务便签，不另建角色人格、模型记忆或多份待办。切换模型时继承已确认事实，只核对本轮依赖的证据，不重复整仓阅读或已有验证。

| 角色 | 默认职责与可写范围 | 边界 |
| --- | --- | --- |
| Astra | 系统架构取舍、跨模块责任设计、主人点名的审查；交付必要的约束与理由 | 不充当每轮审批人；无明确授权不顺手实现功能、不派生新的审查轮 |
| Luna | 读源码、取证、制定和修订局部计划、实现、排障、自验、更新文档；可在授权目标内选定下一小步 | 保持产品目标、架构契约与验收要求；不扩大产品范围、不操作真实凭据、不降低安全边界；遇到第 6 节的架构决策才升级 |

角色不改变原有授权：发布、推送、消息和付费测试仍按已有边界处理。Luna 发现局部计划有误，可根据证据直接修订 plan 和交接卡并继续；不必因文件清单、实现方法或测试范围需要调整就转交 Astra。若证据要求改变产品目标或架构契约，才记录具体冲突并进入“需复核”。

### 唯一交接卡

在 status 顶部维护一张卡，不新建角色记忆文件、第二套任务清单或不同模型的计划副本。卡片至少包含：

- **任务标识 / 修订**：稳定短标识和修订号；新目标换标识，目标/范围/验收发生实质变化才增修订，结果更新不增修订。
- **阶段 / 本轮角色来源**：阶段取“规划中、可执行、执行中、需复核、待主人验收、已完成”；记录主人本轮指定角色的依据。
- **目标 / 方案入口**：指向 plan 的确定小节；纯工作流维护可指向本文。不把未来路线直接当本轮方案。
- **本轮允许与禁止范围**：仓库、文件/模块；模型请求和外部动作边界。具体文件清单可引用 plan，避免两处漂移。
- **验收 / 停止点**：本轮用哪些证据判定完成、由谁验收、完成后是否停。
- **完成证据 / 下一接手**：已发生的结果、未验证项、实际提交或未提交状态；下一角色及入口。明确可执行时以“已就绪：”开头并链接plan唯一下一轮；没有合格下一任务写“无就绪下一任务”，允许plan没有下一轮。纯工作流维护的当前目标可链接workflow。

接手时先核对卡片与 Git 实际状态。上轮的“我已完成”是待核对记录，不是本轮亲自运行过的测试；发现矛盾就纠正现状，不能照抄成自己的验证。旧执行步骤从 status 移除，命令留在 README，历史交给 Git。

### 切换与停止规则

1. 每轮开头说明“本轮按 [角色] 处理 [任务标识/修订]，做到 [停止点]”，无需反复向主人确认已明确的角色。
2. 没有新角色声明而仍在继续同一未完成任务时，沿用主人最近明确指定的职责；不能因为卡片写了“下一接手 Luna”就自动成为 Luna。新任务且没有可用角色依据时，先做只读核对，写入前用一个简短问题澄清角色。
3. Luna 可自行补齐局部计划的范围、验收和停止点，更新卡片为“可执行/执行中”后实施，无需 Astra 签字。“可执行”不替代主人授权；主人只要求讨论或审核方案时，仍停在方案交付。
4. 主人说“继续/推进”时，Luna 可按当前阶段已确认目标选一个最小下一步并更新卡片，不重做旧任务、不跳到暂停或未来工作线。只有角色声明而没有工作请求时，不自行开工。
5. 角色与任务不匹配时不自动冒充另一角色、不擅自改卡放行。完成相关只读核对后说明缺的是角色调整还是具体方案；已有明确指令足以消除冲突时直接同步卡片，不增加形式化审批。
6. Luna 对内部闸自行验收并记录；涉及主人可见行为按既有规则进入“待主人验收”。完成明确的小轮后停，不自动跨轮；发现架构冲突时仅暂停依赖该决策的部分，完成其余范围内工作。

交付末尾简短写明当前角色、任务结果、下一接手与是否就绪。同一 session 的历史和摘要用于找证据，当前任务取本轮指令与最新文件；压缩后也先恢复交接卡，不重复已完成工作。本约定是可审查的协作规则，不是技术沙箱，不能声称能自动识别实际模型或绝对防止越界。

## 1. 每一轮

1. **接手**：AGENTS → status → [plan](plan.md) 当前方案 → 本轮相关设计或证据小节；查 Git 工作树。只为准确定位本轮而读，不默认加载完整 adapter、旧方案或归档。缺少当前任务必需材料按 AGENTS 停止，不能猜。
2. **确定一小步**：说明本轮用户能看见的结果和范围。正常实现选择自己判断，不把一长串设计问题退给主人。评估不等于开工授权，验收通过也不等于允许无限扩展。
3. **实现**：先证据再契约，再状态与派生视图，最后接 UI。视觉改动对照真实正本，不重做已经通过的部分；发现阻塞及时说明。
4. **机读验证**：跑适用的类型、单测、控件、边界、demo、证据、文档检查。测试覆盖真实风险和失败路径，不写镜像实现的空断言。失败修实现或更正结论，不能放松闸。
5. **交付并等待验收**：先说明改的是哪个仓库、用户会看见什么变化，再并列已完成、未做与未验。可见交付给具体命令、入口、配置、3–5 步动作与预期；纯文档交付给阅读入口，不让主人跑无关程序。机读结果独立列出。内部闸由执行者自行判断；只有真实 UI、用户操作路径、视觉布局或需要主人决策的行为才请主人验收。
6. **收口**：内部闸通过后即时更新 status 并继续已授权范围；用户可见验收仍按主人反馈收口。部分通过就准确记录范围；不通过先修失败项；主人接受的限制留在已知限制中，不抹掉也不反复擅自重开。

### 任务准入与停止规则

新任务必须满足至少一个具体触发，并在status交接卡写出依据：

| 触发 | 必须说明的证据 |
| --- | --- |
| 已发生的错误 | 失败日志/可重复用户症状、具体文件或调用路径；故障首次归类不是已解决 |
| fork改动的实际影响 | 具体diff或提交→受影响调用链→可观察风险；不能只说“改了环境/品牌所以全引擎可能有问题” |
| 已确认交付要求尚缺 | 例如自己的包身份、实际安装平台、升级或已有承诺的提醒功能；使用现有工程，不另造重复入口 |

没有这些依据，只有“没亲自测过、也许不安全、还能测得更全面”，不得立项、不得列发布阻塞。未修改且无失败信号的继承模块保留正常适用回归，不重写一套专项证明。上游发行不是忽略真实失败的借口，缺少自己专项证据也不是已有能力损坏的证明。

立项只需同一张交接卡中的一句触发依据、受影响范围、完成条件，不增加审批或另开规划轮。普通实现/测试修复Luna自主完成；新出现的真实失败可登记并按因果链处理，无需等Astra逐条批准。

- 开始先读已有源码、既有回归和Git差异，再运行最小的受影响文件集；同组根因在一轮内成组修，不按每个断言拆轮。
- 正常小轮先定结束条件，完成就本地提交。结果“尚未覆盖X”只限定证据，不自动指定“下一轮做X”。下一入口只能来自status未闭合失败/交付欠账；没有合格任务就停止，不自行创造审计。
- 不重复已经通过且没有受相关改动影响的检查。仅改文档不跑引擎；仅改测试且复用同一生产产物，不例行重新构建。重跑应说明触发：新改动、前一次未执行成功、或具体不稳定性证据。发布候选集中跑现有适用总闸及真实包安装检查。
- 错误要有根因、修复/处置和复验才关闭。过时断言依据已确认契约更正，保持行为/安全检查强度；不能删断言、无依据skip或改产品迎合旧品牌。平台不适用/功能退役要给依据和相应适用覆盖。
- 全绿不是Git保存前提。未修完也WIP保存；全绿也不等于产品验收、安装或发布批准。

### 编辑和命令执行的最低成本保护

现有Git基点→一次局部补丁/脚本→语法与diff→相关测试→本地保存。脚本与产品缺陷分开归因，执行失败不得声称成功。

Python固定UTF-8、newline为LF；涉及日志的脚本固定stdout UTF-8。传递复杂文本用UTF-8数据文件，避免跨JS/Python/PowerShell多层转义；原内容校验通过才写。临时Python先用compile()检查，新增JS/TS先做对应语法/类型或定向装载检查；不要先启动昂贵集成才发现引号错误。上述都是每次编辑的一次轻量检查，不新建大型检查系统。

Shell仅作简单调用。串行依赖必须检查退出码：修改脚本失败后不得继续跑基于新内容的测试；测试失败允许明确WIP保存，但不能因后面的git成功覆盖前面的失败状态。工具遇到权限拒绝按工具审批机制处理，不绕过沙箱或盲换工具。两次相同调用/转义错误后停止同一写法，改用已验证的简单方式，不用反复试错烧token。

### 向主人报告什么

固定报告：本轮解决的实际问题/交付；实际改的是生产代码还是测试/文档；验证与未验范围；本地提交号；下一个现存失败或交付欠账。用成果而非“又测了几个边界”表示进度。没有基于实际剩余工作的估计就不报固定轮数/发布日期，也不每次另开规划。技术自验不交给主人看JSON。

### 每轮局部计划

本轮承担者（通常为 Luna）先核对已有能力，把本轮写成可执行的小任务，不另开规划轮。每轮明确：复用入口与源码依据、具体改动、涉及模块、验收方法、范围边界和停止点。已有能力满足需求时优先复用；“让验收方便些”不自动成为另建配置界面的理由。

Luna 按范围实现、修复和自验；局部计划错误自行修订并记录理由，不用新功能绕开矛盾。需要架构决策时按第 6 节升级。

真实模型请求前，计划者须说清本次新增证据是什么、为何已有证据或离线测试不足、实际启动哪个构建产物、预计模型回合与连接测试次数以及停止条件。版本号相同不能证明执行的是 fork；“连接测试”可能也发送生成请求，不能只计算显式 prompt。能用源码、假 provider 或既有 trace 证明的内容先离线完成；没有新的待证命题就不重复消耗模型额度。已有授权内的必要请求不重复索要许可，但授权不替代必要性判断。例行检查不得隐含真实模型调用。

## 2. 验收说明怎么写

先写清要验什么、需要的临时目录、已配置的引擎与模型。给主人自己在外部终端执行的准确启动命令，以及实际 URL 或 exe 绝对路径。不要交付只有代理后台服务活着时才有效的窗口。

每步采用“动作 → 可见结果”。例如文件审批的最小场景：在可丢弃目录请求 `请创建 acceptance-note.txt，内容仅为 acceptance-ok。不要修改其他文件。`，先拒绝并确认无文件，再用新测试会话执行批准场景、确认真实落盘，避免前一会话的权限规则干扰。只有源码和设置已确认会触发审批时才使用此场景；prompt 不能保证引擎权限策略生效。作用域证据见 [adapter](adapters/minimax-code.md)。

历史恢复的最小场景覆盖：发送 → 等待真实输出 → 切换/重新打开 → 查看原记录是否单份 → 新 prompt 是否可发送。中断既要观察按钮反馈，也要核对回合结局；看不到权威结局就报“未确认”。选目录则验确定自动导入、取消不改路径、失败或超时恢复按钮。

机读检查不能替代以上验收。错误截图只作排障证据；README 宣传截图必须来自当前正常版本或主人指定的图，不能把 bug 截图当产品图。展示大图先压实际字节体积，不是只改显示宽度。

## 3. 文档流与冷启动

| 问题 | 唯一落点 |
| --- | --- |
| 现在好了什么、还缺什么、下一入口、主人决定 | status |
| 当前实施方案、分轮验收目标、未来阶段的规划入口 | plan；不记录执行进度或重复主人决定账 |
| 如何启动和检查 | README |
| 有哪些硬规矩、文件去哪找 | AGENTS |
| 如何协作与验收 | 本文 |
| 视觉为何如此、范本在哪里 | design |
| MiniMax 到底会返回什么、有哪些有损映射 | adapters/minimax-code |
| 跨引擎仍有价值的踩坑经验 | lessons |

不要把源码事实、当前进度和历史事故混在一篇里。现状过时就改，不追加“其实已完成”留着旧矛盾。路径变动同轮修链接；重要决定当轮落盘，不能留到上下文将尽。整篇替换才归档，归档顶部指出替代文档；冷启动不默认读取归档。

## 4. 工程建立后的检查要求

当前可运行闸以 README 和 package.json 为准；已有类型、核心测试、demo 和交接检查，控件清单、模块边界及构建闸尚未完整落地。下表是完整要求，不代表均已实现。不复制 Rhodes 的计数、禁止词表、kind 表来制造通过。

| 检查面 | 要证明什么 |
| --- | --- |
| 类型 | 产品和测试严格类型检查 |
| 单测 | 请求关联、迟到响应、去重、错误恢复和跨目录状态等真实风险 |
| 控件 | 元素清单、接线、资源、动态控件、无静默失败 |
| 模块边界 | UI / view 不导入适配器、宿主、主入口 |
| demo | 范本资源、ID、语法、减少动态效果支持 |
| 文档与证据 | 映射结论与可复现 trace 一致；缺证据不能标已验证 |
| 文档链接 | 当前相对链接与权威路径有效 |

产品工程建立后用 `npm run check:all` 聚合以上适用闸；未实现的闸明确登记，不造空壳成功脚本。桌面阶段另加 Cargo fmt/check/clippy、必要宿主测试、生产构建资产检查。小轮只跑受影响检查；发布候选及仓库明确要求的PR验证再跑适用总闸。本地WIP保存无需总闸通过，不受未知泛化风险阻挡。

## 5. 服务、资产和 Git

开发窗口与长服务由主人在外部终端启动，代理给命令、运行有限检查、说明版本/端口；不要因代理任务结束杀服务，不用模糊进程名批量清理。宿主只收回自己拥有的子进程。

提交前查看 staged 清单、体积、产物和敏感数据：Rust `target/`、前端 `dist/`、依赖、引擎数据、凭据、日志、私人会话不入库。引用图默认仅本地设计参考，不自动进产品包。公开发布前核对素材与字体授权；此项不得写成已完成。

本地 Git 防损要求（主人 2026-10-01 明确纠正）：Git 是时间恢复工具，保存与质量验收相互独立。

1. 修改前检查两个仓库的工作树和当前提交；现有未提交源码先保存为本地 WIP 提交，再动文件。无需等待测试通过；工作树已干净则使用现有提交作为基点，不制造空提交。
2. 小轮完成、失败或交接时都保存本轮源码进展；失败/未验证提交标注 WIP，正文说明已知问题，status 记录提交号。已验证提交记录实际检查范围，不能把 WIP 当验收或发行许可。
3. 每次只纳入已检查文件清单的源码、测试和文档；凭据、私人会话、依赖、构建产物和原始日志不入库。文件清单检查不等于全库质量检查，不据此拖延恢复点。
4. 本地提交默认获授权，push、发布和上游合并仍需独立授权。不得为清理工作树丢弃改动，不用整库 reset/checkout 撤回用户成果。
5. 已知失败按根因成组修复并保存；Git保存不扩大为修完所有测试。仅在新改动影响、尚未成功执行或具体失败证据要求时重复相关检查。

Windows 编辑要求：优先局部补丁；需要脚本时优先 Python（Path.read_text/write_text 显式 encoding="utf-8"），避免 PowerShell 的复杂拼接与默认编码整文件读写。PowerShell 可用于简单启动、环境变量和必要系统操作；不能熟练可靠操作时立即改用 Python，不反复尝试有损写法。每次编辑立即检查 diff；发现无关中文/特殊字符变化就停止编辑并修复，不能当作旧问题、不能放宽断言来过关。

提交与推送权限以 status 的当前授权为准。搬过来的 demo 是视觉资产，不能连同整个旧仓的 `.git`、环境、配置和 traces 一起复制。

## 6. 复杂规划的复核与模型交接

保留 **“此处可能需要 Astra 把关”** 作为架构风险提示，不把整个模块指定为 Astra 专属。是否升级按具体决策判断，不按“数据、登录、网络、发布”等关键词判断。

## 宿主环境防损

临时cwd、HOME和dataDir不等于系统隔离。启动引擎的测试须确认注册表、shell配置和全局安装的写入边界；默认测试不得启用持久化shell PATH集成。进程内PATH注入保留，禁止将临时工具目录注册进宿主PATH。

涉及宿主设置的修复先备份原值与类型，限定改动项，提供冲突检查与恢复入口；源码Git不能替代系统设置备份。相关测试对照启动前后宿主值，不从退出码0推断无副作用。工具被审批拦截或未执行目标动作，不能登记功能通过。

交给主人验收的候选和启动入口必须与技术侧检查相同；保留调用者cwd和环境。只复核相关改动或具体失败，不追加全库审计。
